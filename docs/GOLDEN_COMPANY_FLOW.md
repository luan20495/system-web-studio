## 2. Notes that change how the steps must be read

* **N-1 — "Project" and "App" are one entity.** The backend has one table, `projects`; the Studio calls the list "Ứng dụng" (applications) (src: `ProjectController.kt`, `features/studio/StudioApp.tsx`, `features/studio/base.ts`). The brief's step 05 ("create Project") and step 11 ("create App") therefore cannot be two different API objects. This document maps 05 = create the project record (Workspace Admin, `POST /projects`) and 11 = the Editor's first authoring of the application definition inside it (`PATCH …/schema`). UNVERIFIED: whether the owner intended a separate concept; confirm before publishing.
* **N-2 — Step 05 cannot be done by the Tenant Admin, so the first Workspace Admin account is created in step 04.** A Tenant Admin who is not a workspace member gets `404 WORKSPACE_NOT_FOUND` on that workspace (src: c6 `ON17`, `AccessEvaluator.kt`), and `POST /projects` needs `PROJECT_CREATE` + membership (src: `ProjectController.kt`). The product's own Admin dialog creates the workspace and its first Workspace Admin in one action (src: c5 `e2e-admin01`). Strict order 04 → 05 → 06 is only executable this way.
* **N-3 — Requester and approver must both be `WORKSPACE_ADMIN` today.** `WORKFLOW_EXECUTE`, `DATA_MUTATE`, `DATA_SOURCE_MANAGE`, `WORKFLOW_MANAGE` are held by no project role (src: `Permission.kt` comment "NOT held by any project role … until explicit grants exist (sharing, T15)"). The approval route needs `WORKFLOW_MANAGE` (no `APPROVAL_DECIDE` in this RC, src: c4a `docs/parallel/audit/C4-FQ-WF-01-approval.md`). A realistic "employee requests / manager approves" split without workspace-admin rights is a PRODUCT GAP (DEFERRED).
* **N-4 — No browser UI starts a LIVE action/workflow or decides an approval.** Studio runs actions/workflows in `mode: "TEST"` only (src: `features/studio/ProjectWorkspace.tsx:151-153`); a published PAGE_SCHEMA page only runs public READ queries (src: `workers/render/page-runtime.ts`); `packages/api-client/src/api.ts` has `startWorkflow`/`workflowRun`/`cancelWorkflowRun` but **no** approval-decision method (grep of `features packages lib apps` on integration and on c4a finds none). Steps 17–20 are therefore API-driven (as the C6 harness did).
* **N-5 — A LIVE run needs an ACTIVE release, so one PRIVATE release exists before step 17.** `mode: LIVE` resolves the version of the active release; "no pointer = nothing published = 404" (src: `contracts: runtime-api` §1; c6 `J06-S03`). Release numbering used below: **R0** = bootstrap PRIVATE release published before step 17; **v1** = the PUBLIC release of step 21; **v2** = step 24. Rollback in step 25 targets v1.
* **N-6 — Organization relations never authorize.** `MANAGER`/`HEAD`/position/grade grant nothing (src: `contracts: tenant-permission` §5c.3–4). The approver is an explicit user id. The Studio approver field is a free text box (`aria-label "Mã người duyệt"`, src: `features/studio/builder/WorkflowEditor.tsx:111-113`); whether a picker exists is UNVERIFIED. `PrincipalSpec` kinds `ROLE`/`GROUP`/`DEPARTMENT_MANAGER` are resolved once when the step starts and C1 answers "users/roles only" (src: c4a handoff "Known limits").
* **N-7 — UI default vs backend default (approval).** The Studio checkbox "Cho phép người khởi chạy tự duyệt" is checked when `allowSelfApproval` is absent (`checked={a.allowSelfApproval !== false}`) and the expiry hint says "Để trống: không hết hạn", but the backend defaults `allowSelfApproval=false` and `expiresInSeconds=86400` (src: `WorkflowEditor.tsx:121-122`; `CanonicalWorkflowCatalog.kt:119` on c4a). Read from source, not observed in a browser: UNVERIFIED in runtime.
* **N-8 — Contract vs code (code wins).** `contracts: tenant-permission` §4 says a platform-scope SYSTEM_ADMIN also holds `MEMBER_MANAGE` and `PROJECT_CREATE`; `PermissionMatrix.platformScope` contains only `TENANT_MANAGE` and `TENANT_MEMBERS` (src: `Permission.kt`). C6 recorded one P3 about the same area: `GET /workspaces/{W}/projects` as a non-member system admin answers `200 []`, contract says 403 (src: c6 `ON65`, `FQ-IAM-01`).
* **N-9 — No notification to the approver.** `notifyTemplateRef` is not wired; the manager is not told (src: D-C0-61 item 5). There is no approvals inbox/list route (DEFERRED).
* **N-11 — The public-data approval gate exists only once a publish policy is stored.** `POST …/publish` with `visibility:"PUBLIC"` and **no stored publish policy** is accepted without any public-data approval (compatibility path: `requirePublicDataApproval` returns early when no `publish_configs` row exists); `409 PUBLISH_POLICY_MISMATCH` and `422 PUBLIC_DATA_NOT_APPROVED` apply only after `PUT …/publish-config` stored a policy. The Public Runtime still refuses queries without `public_data_approved` (src: `PublishController.kt` `requirePublicDataApproval`). The golden flow stores a PRIVATE policy first when it wants to exercise the gates.
* **N-10 — Known open IAM risk touching steps 02/04/06.** The activation link of a created account is returned to the creator, so a Tenant Admin can activate and log in as the Workspace Admin they created; recorded P1 awaiting a C0 decision (src: c1h `docs/parallel/c1/final-iam-hardening-report.md` §3).

### 3.3 Data target and trust store (steps 13–15, 20, 23)

* The connector verifies TLS `verify-full` against the **JVM** trust store and a tenant can never add a CA. The data target's dev CA must be in the backend JVM trust store: `scripts/data-target.sh` merges the dev CA with the JDK `cacerts` into `.run/data-target/truststore.jks`; the stack passes it as `JAVA_TOOL_OPTIONS="-Djavax.net.ssl.trustStore=… -Djavax.net.ssl.trustStorePassword=…"` (values live in the stack's env file, never in documents) (src: D-C0-59 item 4; `scripts/_env.sh:50-51`).
* A private target must be named exactly as `host:port` in `DATA_PLATFORM_POSTGRES_ALLOWED_PRIVATE` (the local profile allows only `127.0.0.1:15440`); the platform and apps databases are always denied; any other private/loopback/link-local/metadata address is refused (src: D-C0-31; `application.yml` `postgres-targets`).
* Without the trust store, *Test connection* answers `{ok:false, code:"TLS_FAILED"}` — this blocked Journey 05 on stack `c0rc` before D-C0-59 (src: c6 `FINAL_RC_QA_REPORT.md` FQ-ENV-01; D-C0-59 item 4).
* The writable source needs `config.writable="true"` and a non-superuser role with INSERT/UPDATE (src: D-C0-31 item 7; c6 `J05-M00/M01`).

### 3.5 Conventions used by every API field

* Base `/api/v1`. Browser calls carry the session cookie (HttpOnly) and, on every state-changing call, `X-XSRF-TOKEN` (`GET /api/v1/auth/csrf`); missing/bad CSRF = `403 CSRF_INVALID`, not signed in = `401` (src: `contracts: management-api` §1.3).
* Error envelope for runtime/management routes: `{"code","message","requestId","retryable","details"}`; platform routes return `ApiError` (src: `contracts: management-api` §4, `runtime-api` §1).
* A foreign, unknown or other-tenant resource is a safe `404` (`WORKSPACE_NOT_FOUND`, `PROJECT_NOT_FOUND`, `TENANT_NOT_FOUND`, `NOT_FOUND`); `403` is returned only to a member who lacks the permission (src: `contracts: management-api` §1.5; `AccessEvaluator.kt`).
* Bodies are strictly parsed: an authority-looking key (`tenantId`, `workspaceId`, `userId`, …) or an unknown key is refused `400` (`INVALID_REQUEST` runtime, `INVALID_PARAMS` management).
* Ids: `{t}` tenant, `{ws}` workspace, `{p}` project, `{ds}` data source, `{run}` workflow run, `{ap}` approval, `{dep}` deployment. Secrets are never placed in any request in this document: usernames are fictional, passwords come from the environment.

## 4. The 27 steps

### 01 — System Admin creates Company

* **ACTOR:** System Admin (platform account).
* **UI_PATH:** Platform portal `/platform/tenants` → "+ Tạo công ty" dialog (fields `tenant-slug`, `tenant-name`; the dialog picks the first admin from an existing account) → lands on `/platform/tenants/{t}` (src: c5 `e2e-pl01`; `features/admin/console/sections.tsx` key `tenants`).

* **ERROR_CASE:** duplicate slug → `409 TENANT_SLUG_TAKEN`; malformed slug → `400 TENANT_SLUG_INVALID`; blank/over-long name → `400 TENANT_NAME_INVALID`; caller not a system admin (including a Tenant Admin) → `403 ADMIN_REQUIRED` (src: c6 `ON03`, `ON04`, `ON13`; `TenantService.kt:47-49`); `firstAdmin` with a taken username → `409 USERNAME_TAKEN` and no tenant is left behind (src: `CompanyBootstrapService.kt`; test `CompanyBootstrapTests`); missing CSRF → `403 CSRF_INVALID`.

## B. Reference — UPDATE_RECORD changes a real row (FQ-ACT-02)

Source: `docs/parallel/audit/C4-FQ-ACT-02-record-key.md` (branch `fix/c4-fq-act-02`, imported by D-C0-58); code + tests are on integration.

* **Defect (before):** the action input `recordId` was forwarded unchanged to the PostgreSQL connector, where "a parameter's NAME is its column name"; an approved mutation `target: "shop.items key=id"` with params `[id, status]` therefore failed `INVALID_PARAMS` (HTTP 500) — only a table with a physical column literally named `recordId` worked.
* **Rule (after):** the approved mutation already names its key: `target := [schema.]table key=p1[,p2…] [returning=…]`. `MutationExecutor.recordKey(def, ds)` (PostgreSQL: the single key parsed by `PgMutationTarget`) and `RecordKey.resolve(def, keyParam, given)` map `recordId` → that parameter before `QueryParams.bind`. Only UPDATE/DELETE; only when `recordId` is given; only when the definition does not declare its own `recordId`; only when exactly one key is reported and it is a declared parameter; `recordId` plus the key itself → `INVALID_PARAMS` (ambiguous); an INTEGER key accepts a whole-number text. CREATE/SUBMIT never alias.
* **Result:** `POST …/actions/update-item/execute {"inputs":{"recordId":"<id>","status":"shipped"}}` → `200 {"status":"OK","output":{"operation":"items.update","kind":"UPDATE","affected":1,…}}`, SQL `UPDATE "shop"."items" SET "status" = ? WHERE "id" = ?` with bound values.
* **Security:** the physical column comes only from the approved definition (identifier pattern, configured schemas, quoted); every value is a bound parameter; authorization (`ACTION_EXECUTE`, `DATA_MUTATE`, `MUTATION_EXECUTE`), tenancy and idempotency are untouched; an ambiguous timeout leaves the key `UNKNOWN` (`IDEMPOTENCY_OUTCOME_UNKNOWN`, `retryable=false`, one statement reached the database, no compensation).
* **What the operator configures:** `target:"shop.orders key=order_no"` with a declared parameter named `order_no` (STRING for text/uuid keys, INTEGER for bigint); the action keeps the input `recordId`. The key column name must match `[a-z][A-Za-z0-9_]{0,39}` (a column such as `OrderId` cannot be a key parameter — pre-existing limit).
* **Known limits (not changed):** a missing row succeeds with `affected: 0`; `INVALID_PARAMS` answers HTTP 500 (C0 `RuntimeResponses`; 422 would be right); the C6 retest on the exact RC SHA has not been recorded (`FIXED_PENDING_C6_RETEST`, D-C0-58 item 2, D-C0-59 item 5).
* **Evidence:** `RecordKeyGatewayTests` 14/14 and `RecordKeyActionE2ETests` 7/7 recorded in the handoff (before the fix 8/14 and 5/7 failed); regression 1099 tests / 1 unrelated wall-clock failure (handoff §6).

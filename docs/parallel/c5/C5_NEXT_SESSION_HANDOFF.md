## 10. FQ-PERF-01 (duplicate `/auth/me`) - FIXED
- **Root cause (production behaviour, not Strict Mode):** all three portals mounted `SessionProvider` INSIDE the page (`PortalApp`). Under `app/[[...slug]]/page.tsx` Next gives every path its own page key, so every path change (login -> portal, every sidebar link) REMOUNTED the provider: its mount effect read `/auth/me` again, behind a full-screen splash. After a sign-in that is two reads back to back (`api.login` reads it, then the remount reads it again; ~0.4 s on a fast machine). Measured on production builds of the three portals against a real backend, with a stack trace of each fetch (`Object.login` then `Object.me` from the provider effect). Strict Mode doubles only the development case.
- **Fix:** `SessionProvider` moved to the ROOT LAYOUT of Platform / Admin / Studio (`apps/*/app/layout.tsx`, survives navigation); nested providers (`PortalApp`, harnesses, the legacy app) render their children unchanged; the read is single-flight; a path change while a session is held re-reads `/auth/me` in the background (no splash); the sign-in that just read it hands the answer over (`setMe`) so the navigation it triggers does not read again; a read that started before a logout / replacement is dropped (generation counter); a transient failure of a background re-read keeps the last answer (the server still authorises every call), a 401 ends the session, ACCOUNT_DISABLED blocks. `packages/auth/src/session.tsx`.
- **Security:** no stale authorization cache was introduced: authorization is still re-read on every path change, so revocation, a disabled user, a suspended tenant, changed memberships and a switched company / project become effective at the next navigation exactly as before (before: also at the next navigation, but through a splash); the server authorises every call regardless.
- **Counts (real backend, production builds, `/auth/me` requests):** cold load of a console URL with no session: 1 (401 probe). Sign-in: BEFORE 3 (probe, login read, remount read), AFTER 2 (probe, login read) on Platform, Admin and Studio. One sidebar navigation: 1 (background revalidation) and no splash; a click that does not change the path: 0.
- **Tests:** `admin.spec` FQ01-FQ07 (cold load 1; navigation 1 and no splash; same path 0; 503 keeps the session; 401 ends it; ACCOUNT_DISABLED blocks; revoked permissions effective at the next navigation), 193/193 Chromium. Real: stale session (cookie gone) -> `/login`; logout -> `/login`, direct console URL -> `/login`, privileged nav never rendered; AD01 / AD03 / SUPER01 / ADMIN01 / USER01 / SEC01 / ORG01 PASS. `E2E-PL01`'s restore check now polls the server instead of a fixed 800 ms wait (it was flaky on the old code too: 1 of 2 runs).

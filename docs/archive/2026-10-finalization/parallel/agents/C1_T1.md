## 2. Current architecture (đã đối chiếu code thật)
- **Modular Monolith** Kotlin 2.2 / Spring Boot 4.1 / JDK 21 / Jackson 3 (`tools.jackson`), package gốc `com.systemwebstudio` ở `backend/src/main/kotlin/...`. **Không phải microservices** — không được đề xuất/chuyển sang microservices.
- Backend khoảng 105 file Kotlin, ~20 module: `access admin ai asset audit code common component identity integration maintenance member project prompt publish runtime schema settings template version`.
- **Frontend Next.js ở ROOT repo** (không có thư mục `frontend/`): `app/ features/{admin,auth,studio} components/ lib/ e2e/`.
- PostgreSQL + Flyway (hiện tới **V25**), Redis (session), MinIO, RabbitMQ.
- Ngoài JVM có các plane riêng: render worker, build runner, Forgejo, nginx/site gateway, generated app containers.
- Hiện **chưa có**: multi-tenant thật (không có bảng `tenants`/`tenant_id`), Tenant Admin, group/department permission thật, ABAC, RLS, App Model hợp nhất, metadata DataSource/Query/ViewModel/Mapping/Transform, Schema Discovery, metadata Event/Action/Workflow. Đơn vị tổ chức thực tế là **Workspace**; Super Admin = `users.system_admin`; Tenant Admin gần nhất = `WORKSPACE_ADMIN`; quyền = workspace role + project role (`PermissionMatrix`); Department chỉ để báo cáo.
- `projects` chứa hai kiểu app: **PAGE_SCHEMA** (metadata JSON; AI sinh typed operations → `SchemaPatchEngine` → `PageSchemaValidator` → version bất biến; AI không sinh code tùy ý) và **STATIC_APP** (source trong Git/Forgejo, build sandbox, container có DB riêng). V2 **không** rewrite; V2 mở rộng PAGE_SCHEMA thành App Definition V2 theo hướng backward compatible.

Luồng dữ liệu chuẩn (đích): `UI → App Definition/ViewModel → Query|Action → Auth → Permission → Data Gateway → Connector → DB/REST/External → Mapping/Transform → UI`.
Luồng AI chuẩn: `Prompt → Structured Operation → App Definition → Validator → Version`. **AI không có model dữ liệu riêng.**

## 6. Migration rule (DUY NHẤT)
- Flyway hiện ở **V25**. Agent **KHÔNG tự chọn** migration version, **không tạo** file migration khi chưa được cấp số.
- Cần migration → ghi request vào mục *Migration requests* của `docs/parallel/BOARD.md` (task, requester, mô tả thay đổi schema). **C0 cấp next available version** (V26, V27, …). Một version gắn với đúng một task. Migration được merge theo thứ tự tăng dần. **Không bật `outOfOrder=true`.** Không sửa migration đã tồn tại (V1–V25). Không đổi tên bảng `projects`.
- Chưa được cấp số → dừng phần cần DB đó, ghi request, làm phần còn lại.

## 8. Task objective
Kiểm toán **cô lập dữ liệu và kiểm soát truy cập theo đối tượng** (IDOR/BOLA) của toàn bộ API hiện tại, rồi viết test chứng minh: **user A không thể đọc/ghi tài nguyên workspace/project của user B** ở mọi endpoint được audit. **Đây chưa phải Tenant.** Không implement tenant, không tạo bảng `tenants`, không đổi kiến trúc quyền.

## 9. Exact scope
1. Đọc toàn bộ controller/service/repository liên quan: `project`, `member`, `schema`, `version`, `prompt`, `asset`, `publish`, `ai`, `runtime`, `code`, `template`, `component`, `audit`, `settings`, và các endpoint `admin/**` có resource context (workspace/project id trong path/body/query).
2. Lập **endpoint inventory**: method + path + controller + cách xác định quyền. Phân loại từng endpoint:
   - **Protected**: đi qua `AccessService.forWorkspace(userId, workspaceId)` hoặc `forProject(userId, workspaceId, projectId)` và `AccessContext.require(...)` với permission phù hợp, **và** mọi truy vấn con (version, prompt, asset, deployment, domain, form submission…) bị ràng buộc theo `project_id`/`workspace_id` đã xác thực.
   - **Suspect**: tìm tài nguyên trực tiếp theo id (repository `findById`, JdbcTemplate theo id trần), tin `workspaceId`/`projectId` từ body/query mà không đối chiếu, endpoint không gọi `AccessService`, quyền yếu hơn hành động (ví dụ GET dùng cho thao tác ghi), id của tài nguyên con không kiểm tra thuộc project cha (ví dụ `versionId`, `assetId`, `promptId`, `deploymentId`, `connector grant`, `projectId` trong body).
   - **Public/By-design**: endpoint công khai có chủ đích (site đã publish, form submit, auth, health…) — ghi rõ lý do và kiểm tra không lộ dữ liệu ngoài phạm vi.
3. Xác định nơi chỉ trả 404 vs 403 và đảm bảo **không lộ sự tồn tại** của tài nguyên người khác (quy ước hiện tại: không phải thành viên → 404).
4. Viết **test isolation** (tận dụng `IntegrationTestBase`/`ApiSession`/`TestFixtures` có sẵn, dùng ≥ 2 user ở ≥ 2 workspace/project): với mỗi endpoint đã audit, user A gọi tài nguyên của B bằng id đoán/ghi chèn → phải bị từ chối (404/403), cả đọc lẫn ghi; kiểm thêm viewer không ghi được, user bị disable mất quyền, project ARCHIVED chỉ còn đọc.
5. Lỗi bảo mật nhỏ, nằm **trong ownership C1** (`identity/** access/** member/**`): được phép sửa tối thiểu + test hồi quy. Lỗi nằm ngoài ownership (ví dụ trong `project/`, `schema/`, `publish/`, `runtime/`, `ai/`, `admin/`): **KHÔNG sửa** — ghi blocker `needs-hot-file` kèm file, dòng, mô tả khai thác, đề xuất sửa; C0 sẽ điều phối owner.
6. Viết báo cáo audit vào `docs/parallel/audit/T1-isolation-audit.md` (thư mục mới, thuộc task này): inventory, protected, suspect, test coverage, discovered gaps (mức độ + ownership), đề xuất cho T2 (Tenant foundation).

## 10. What NOT to do
- Không implement tenant/organization/sharing, không thêm bảng, **không migration** (T1 không cần; nếu thấy cần → ghi request, dừng).
- Không đổi chữ ký hay ngữ nghĩa `AccessService`/`AccessContext`/`PermissionMatrix` hiện tại (hot file của bạn nhưng T1 chỉ audit + fix nhỏ an toàn).
- Không sửa file ngoài ownership, kể cả khi lỗi rõ ràng. Không sửa `runtime/Gateway.kt`, `publish/**`, `admin/**`.
- Không thêm GitHub Actions, không đổi API hiện tại (đường dẫn, status code công khai) trừ khi là fix bảo mật trong ownership và ghi rõ.
- Không đụng frontend.

## 11. Acceptance criteria
- Có endpoint inventory đầy đủ cho các controller đã liệt kê, mỗi endpoint được phân loại Protected / Suspect / By-design, kèm bằng chứng (file:dòng).
- Với **mọi endpoint được audit** mang resource context: test chứng minh user A không đọc/ghi được workspace/project của B; thiếu quyền → bị từ chối đúng mã.
- Mọi gap được ghi rõ owner + mức độ; gap trong ownership C1 đã được sửa kèm test hoặc ghi lý do không sửa.
- Không có thay đổi hành vi hợp lệ nào của user đúng quyền (test hiện có vẫn xanh).
